## 2. Problem statement (use this wording in docs)

During evening peak demand (about 18:30-22:30 **[VERIFY: CEB time-of-use peak window]**), many Sri Lankan distribution feeders experience sustained under-voltage. Equipment such as compressors and motors draws more current at low voltage, which worsens the sag and can damage equipment or trip protection. Hospitals and similar critical facilities need a stable supply voltage during these periods and during full outages.

GridGuard is a supervisory energy-management system for a critical facility with grid, solar, battery, and generator. Its digital twin forecasts the facility's energy balance and grid quality, decides when to support the critical bus from the battery, which loads to shed, and when to start the generator, while minimising fuel and battery wear.

Scope boundary (state this explicitly in the docs):
- **Fast protection** (millisecond transfer, voltage regulation) is performed by power electronics (online UPS / inverter with static transfer switch). GridGuard models its behaviour but does not claim to replace it.
- **Supervisory decisions** (minutes to hours) are GridGuard's job: pre-peak charging, support-mode entry/exit, load shedding, generator scheduling.

## 5. Phase 1: Voltage-aware plant, controller, scenarios, live control

Goal: a convincing demo of peak-hour under-voltage handling with a live parameter-manipulation interface. This is the most important phase for the Track B score.

### 5.1 Physical model

**T1.1 Feeder and grid voltage model** (`physical/feeder.py`)

Voltage at the point of common coupling (PCC) in per-unit:

```
V_pcc_pu(t) = V_source_pu(t) - Z_pu * (P_bg(t) + P_site(t)) / P_feeder_rating  + sag_event(t) + noise(t)
```

- `P_bg(t)`: background (neighbour) load on the feeder. Daily profile with an evening peak, configurable window (default 18:30-22:30 **[VERIFY]**) and peak magnitude. Smooth ramps, not step functions.
- `P_site(t)`: the site's own import, creating the coupling (site current worsens its own voltage). Use a simple, documented linear approximation; state in docs that it is a lumped single-feeder model.
- `sag_event(t)`: generated from the scenario file. Types:
  - `short_sag`: depth 0.1-0.3 pu, duration seconds to a few minutes
  - `sustained_undervoltage`: depth 0.04-0.12 pu, duration 20 min to 3 h, mainly inside the peak window
  - `outage`: V = 0 for a given duration
- `noise(t)`: small Gaussian, seeded.
- Config params: `Z_pu`, `P_feeder_rating_kw`, `peak_window`, `bg_peak_kw`, `sag_events`, `noise_sigma_pu`.

Acceptance: unit tests show (a) V drops as background load rises, (b) V drops further as site import rises, (c) same seed gives identical series, (d) statutory band constants (`V_MIN=0.94`, `V_MAX=1.06` **[VERIFY: ±6% Sri Lanka distribution code]**) come from config.

**T1.2 Voltage-dependent loads** (`physical/loads.py`)

Use a ZIP model per load class: `P = P0 * (a_z*V^2 + a_i*V + a_p)`. Defaults (documented, editable): lighting mostly impedance, electronics mostly constant power, HVAC/motors as constant power with extra current draw below about 0.9 pu. Tiers stay: `critical`, `important`, `non_essential`. Compute each tier's current draw, since low voltage raises current for constant-power loads.

Acceptance: test that constant-power load current rises as V falls; test that tier shedding reduces `P_site` and therefore improves PCC voltage slightly (assert direction, not magnitude).

**T1.3 Inverter / static transfer switch model** (`physical/inverter_sts.py`)

States: `GRID_PASS`, `SUPPORT`, `ISLAND`.
- `GRID_PASS`: critical bus voltage equals PCC voltage (no protection).
- `SUPPORT`: inverter regulates the critical bus to 1.0 pu using the battery (online/double-conversion behaviour); the grid supplies the remainder or charges the battery only if V is in band.
- `ISLAND`: grid disconnected; critical bus supplied from battery, solar, generator.
- Parameters: `inverter_rating_kw`, `battery_max_discharge_kw` (C-rate limit), `efficiency` (flat or simple curve), `transfer_time_ms`, `min_dwell_s`.
- Output: `critical_bus_v_pu` each timestep, plus a `dropout_ms` figure for each transfer.
- Overload behaviour: if requested power exceeds the rating, the inverter limits output and the model reports `critical_bus_v_pu < 1.0` and an `OVERLOAD` flag. Do not hide this.

Acceptance: tests for each state, rating limit, transfer time recorded, overload flagged.

**T1.4 PowerQualityNode** (`physical/pq_node.py`)

Publishes `grid_pq` telemetry at a configurable rate (default 1 Hz simulated). Include optional measurement noise and dropout injection hooks (used in Phase 3 robustness tests).

**T1.5 LocalProtection** (`physical/local_protection.py`)

If no valid command or heartbeat arrives within `watchdog_s` (default 30 s), apply fixed local rules: `V_pcc < 0.92 for 5 s -> SUPPORT`, `V_pcc < 0.80 or outage -> ISLAND`, return to `GRID_PASS` only after `V_pcc >= 0.96` for 10 min. Log every fallback activation.

Acceptance: test with the Mock broker cut; plant keeps the critical bus protected without commands.

### 5.2 Intelligence layer

**T1.6 Voltage-aware mode state machine** (`intelligence/decision_engine.py`)

Modes: `NORMAL -> SUPPORT -> ISLAND -> GENERATOR_ASSIST`, with explicit transitions and hysteresis.

| Transition | Condition (defaults, all configurable) |
|---|---|
| NORMAL -> SUPPORT | `v_pcc_pu < 0.94` for at least 10 s, or forecast of sag within the next 30 min with probability above threshold (Phase 2) |
| SUPPORT -> NORMAL | `v_pcc_pu >= 0.96` continuously for at least 10 min and `SOC` above the reserve floor |
| SUPPORT -> ISLAND | `v_pcc_pu < 0.85` or grid lost |
| ISLAND -> SUPPORT/NORMAL | grid back in band for the dwell time |
| any -> GENERATOR_ASSIST | Shadow Twin worst-case ESH below the generator-start horizon (existing logic, extended) |

Anti-thrashing rules (extend the existing staircase idea):
- Separate enter/exit thresholds (hysteresis band).
- Minimum dwell time per mode.
- Maximum transfers per hour; if exceeded, hold the more protective mode and log an alarm.
- When a load tier is shed, ignore that tier's forecast until the remaining tiers prove recovery (keep existing staircase logic and add tests that it still holds in sag scenarios).

**T1.7 Voltage-aware ESH** (`intelligence/esh.py`)

Extend the current three-tier depletion simulation:
- Input a `grid_ok[t]` forecast array (boolean or probability) over the horizon. In Phase 1 derive it from a rule: inside the configured peak window, assume the grid is usable only if the last N minutes of V were in band; outside, assume usable.
- When `grid_ok[t]` is false, the critical bus draws from battery + solar + generator only.
- Return both `ESH_island` (grid assumed unusable, the Shadow Twin worst case) and `ESH_expected`.
- The Shadow Twin always evaluates with generator OFF and grid unusable, then the decision uses that value.

Acceptance: tests with a constant load and no solar reproduce the analytic battery-depletion time within a stated tolerance (reuse and extend `validation/esh_validator.py`); tests that a lower `grid_ok` never increases ESH.

**T1.8 Pre-peak charging** (decision engine)

Before the peak window (default starts 17:00-18:00), if the grid is in band and SOC is below `pre_peak_soc_target` (default 0.9), charge within the inverter's limits. This is the proactive behaviour that distinguishes the system from a reactive UPS. Cap charging power to avoid worsening feeder voltage (use a configurable limit).

Acceptance: scenario shows higher SOC at peak start than the baseline; test confirms charge power cap.

## 6. Phase 2: ML forecasting and uncertainty-aware ESH

Goal: a defensible ML component whose value is measured, not asserted.

### 6.1 Design decision

ML provides **probabilistic forecasts** (P10 / P50 / P90). ESH consumes the **pessimistic** quantiles (low solar P10, high load P90), which extends the Shadow Twin "worst case" idea to forecast uncertainty. The rule-based forecaster remains as a fallback.

### 6.2 Data

**T2.1 Data pipeline** (`ml/data/`)

- **Weather/solar:** download historical hourly irradiance, temperature, and cloud cover for the site location from NASA POWER and/or Open-Meteo historical (ERA5-based) **[VERIFY coverage, resolution, and licence]**. Cache locally as CSV with a documented schema; tests and CI must run without network.
- **Load:** hospital-like load profile. Preferred: a documented public building-load dataset **[VERIFY availability and licence]**. Otherwise a synthetic generator with documented assumptions: base load, daytime ramp, HVAC dependence on temperature, occupancy pattern, random equipment events, day-to-day variation.
- **Voltage:** simulator output from T1.1 (clearly labelled synthetic) and, if available, real logs (see 7.6).

**Anti-circularity rules (mandatory):**
1. Training data and evaluation scenarios must use different seeds and different generator regimes (extra stochastic components and regime shifts in the test data).
2. Split chronologically: train on earlier periods, validate on the next, test on a later unseen period (and a different season if possible). No random shuffling.
3. Do not report accuracy on data the model could have memorised from the generating formula without also reporting results on held-out real weather periods.
4. State in all docs which datasets are real and which are synthetic.

### 6.3 Models

**T2.2 Feature engineering** (`ml/features.py`): hour of day (sin/cos), day of week, peak-window flag, lag features (1 h, 24 h, 168 h), rolling means/stds, temperature, irradiance, cloud cover. Features must be computable from data available at forecast time (no leakage; add a test that shifts targets to catch leakage).

**T2.3 Load and solar forecasters** (`ml/train_load.py`, `ml/train_solar.py`): gradient-boosted quantile regression (e.g. LightGBM) for quantiles 0.1, 0.5, 0.9. For solar, optionally predict a clear-sky ratio on top of a physical PV model instead of raw power. Optionally add a small GRU as a comparison model; keep the better one, report both.

**T2.4 Grid-sag risk model** (`ml/train_sag.py`): classifier estimating the probability that `V_pcc < 0.94` within the next 30-120 min from time of day, recent voltage trend, background-load proxy, temperature. If trained only on simulator data, label it "pipeline demonstration; to be retrained on measured feeder data" in all docs. Do not present its accuracy as real-world performance.

### 6.4 Evaluation

**T2.5 Forecast evaluation** (`ml/evaluate.py`): baselines = persistence, seasonal naive (same time yesterday and last week), current rule-based forecast. Metrics: MAE, RMSE, sMAPE (guard against zero), pinball loss per quantile, empirical coverage of the P10-P90 band (target about 80%), average interval width. For the sag classifier: precision/recall, PR-AUC, Brier score, calibration curve. Use expanding-window time-series cross-validation. Output tables and plots to `results/phase2/`.

**T2.6 Model packaging** (`ml/export.py`, `models/`): save the artifacts with `metadata.json` (training period, data sources, feature list, metrics, git commit, library versions). Report model size and CPU inference latency measured on the development machine. Only call it "edge-deployable" if the measured numbers support it; optionally export to ONNX.

### 6.5 Integration

**T2.7 ForecastService interface** (`intelligence/forecast/base.py`)

```python
@dataclass
class ForecastBundle:
    t0: datetime
    step_s: int
    load_kw: dict[str, np.ndarray]     # keys: "p10","p50","p90" per tier
    solar_kw: dict[str, np.ndarray]    # keys: "p10","p50","p90"
    grid_ok_prob: np.ndarray           # probability the grid is usable at each step
    confidence: float                  # 0..1, from recent forecast error
    source: str                        # "ml" or "rule"

class ForecastService(Protocol):
    def forecast(self, telemetry_history, now, horizon_s) -> ForecastBundle: ...
```

- `ESHCalculator` takes a `risk_level` setting: `median`, `pessimistic` (P10 solar, P90 load), or `custom`.
- The Shadow Twin always uses `pessimistic` plus generator OFF plus `grid_ok = false`.
- **Fallback rules:** if the model file is missing, telemetry is stale, inputs are out of the training range, or rolling error exceeds a threshold, `confidence` drops and the service falls back to the rule-based forecaster and logs why. Add tests for each fallback path.
- Inference runs locally with no network access, under 50 ms per call (assert in a test with a generous bound).

**T2.8 Controller integration:** pre-peak charging target and SUPPORT pre-entry can use `grid_ok_prob`; the decision engine logs the forecast source and confidence with every decision (`status/decision` topic).

### Prepared answers (write final versions with real numbers once results exist)
1. **Why this architecture instead of a simpler one?** A fixed-threshold UPS cannot anticipate sags or manage generator fuel; the air-gapped design lets the same logic run unchanged on real nodes.
2. **Why MQTT?** Lightweight publish/subscribe, standard for constrained devices, supports QoS, retained state, and Last Will for liveness.
3. **What if the network is lost?** LocalProtection applies fixed rules and keeps the critical bus protected; demonstrated in S7.
4. **Most important limitation?** Lumped single-feeder model and, unless real logs are used, synthetic voltage statistics; ML sag model is a pipeline demonstration until retrained on measured data.
5. **How did you validate?** Eight-plus scenarios, Monte Carlo with confidence intervals, analytic ESH checks, ablation versus baselines.
6. **Highest technical risk?** Model-to-reality gap for feeder behaviour and the inverter/STS transfer performance; mitigated by conservative thresholds and the FMEA.
7. **One more month?** Collect real voltage logs and retrain/recalibrate; hardware-in-the-loop with a real inverter or UPS.
8. **What could fail in deployment and how is it handled?** See FMEA (sensor failure, stuck switch, generator no-start, forecast error, malformed commands).
